# AUDIT_FIRMWARE_PROTOCOL.md

**Scope:** Forensic protocol analysis of the existing IQOS ILUMA i PRIME companion app.
**Type of work:** Read-only analysis + additive, passive diagnostic instrumentation.
**Explicitly NOT done:** No architecture rewrite, no UI change, no removed feature, no firmware
write, no DFU/bootloader entry, no brute-forced opcode, no invented protocol meaning.

Target device reported by the user:
- Model: IQOS ILUMA i PRIME
- GATT model number: M0021
- Charger software: v135.5.0
- Stick/body firmware: v135.5.0.33
- Holder firmware: v124.6.0.114

## 0. Honesty note on the "541 / 349 / 196" statistics

Before anything else: **these three numbers are real, and the app already produces them** - but
not in the way a first guess would suggest, and it is important to be precise about it.

`DeviceSnapshot.kt` already has exactly three protocol-health counters:

```kotlin
var framesReceived: Int = 0
var framesDecoded: Int = 0
var framesUnknown: Int = 0
```

They are incremented inside `DeviceSnapshot.applyResponse()` (every call to it does
`framesReceived++`, then either `framesUnknown++` + `return false`, or falls through to
`framesDecoded++` + `return true`). They are shown to the user today under "سلامت پروتکل" in the
Advanced tab's technical report (`فریم‌های دریافتی` / `فریم‌های رمزگشایی‌شده` / `فریم‌های ناشناخته`),
generated by `DeviceSnapshot.toReportRows()` / `toPlainText()`.

So: **541 = framesReceived, 349 = framesDecoded, 196 = framesUnknown**, read directly from that
report on the user's device. Two things worth flagging about them, both verifiable from the code
and neither a guess:

1. **They are cumulative for the life of the transport object**, not per-connection.
   `resetLinkState()` (called on every disconnect) resets `rssi`/`mtu`/`bondState`/
   `connectionStartedAt` but deliberately does **not** reset the three frame counters. So "541"
   is the running total since the app process started (or since the last time the report was
   read right after a fresh install), across every reconnect in that time.
2. **349 + 196 = 545, not 541** - a 4-frame difference. The code path guarantees
   `framesReceived == framesDecoded + framesUnknown` at every instant (there is no other
   `return` path in `applyResponse()`), so this is not a counting bug in the formula itself. The
   most likely explanation is that the three numbers were read from the UI (or copied) a few
   frames apart in time - e.g. the report text was captured, then a couple more notifications
   arrived, then the number was re-read a second time - or BLE and USB transports (each carries
   its **own independent** `DeviceSnapshot`) were both used in the same session and the figures
   were combined from two different snapshots. This is **STRONG INFERENCE**, not verified, because
   no raw capture accompanying those three numbers was available to check directly.

**What this means for this audit:** I do not have access to the actual 196 raw unknown frames
that produced that "196" count - only the source code that produced the counter. Sections 5-8
below (pattern analysis of the unknown-frame population) are therefore built from:
(a) exactly the one frame the task supplied (`00 20 01 01 00` on
`77f38a30-2b2c-489a-be71-29e93a04a90a`), analysed in full, and
(b) a structural/architectural analysis of *why* the current code produces unknown frames at all,
which is verifiable directly from source and does not require the raw capture.
I am not going to invent statistics about the other 195 frames I have never seen. Section 6
implements the logging layer that will let the real 196-frame population be analysed next time,
from real captured data.

## 1. Where incoming BLE frames are decoded

- **Byte-level routing / RX entry point:** `BleIqosTransport.processIncomingBytes()`
  (`BleIqosTransport.kt`). Every `onCharacteristicChanged` (both the legacy and API-33 overloads)
  and every `onCharacteristicRead` funnels into this one function.
- **Typed decoder:** `IqosResponse.decode(bytes: ByteArray)` (`IqosResponse.kt`) - a single
  `when`-free, sequential `if` chain keyed on `bytes[1]` (`kind`), `bytes[2]` (`header`),
  `bytes[3]` (`register`). Falls through to `Unknown(hex, "هدر ناشناخته (...)")` when nothing
  matches.
- **Battery characteristic decoder:** `IqosResponse.decodeBatteryCharacteristic()`, used only for
  `DEVICE_BATTERY_CHAR_UUID` and the standard `STANDARD_BATTERY_LEVEL_CHAR_UUID`.
- **Legacy/duplicate decoder:** `IqosProtocol.parseIncomingFrame()` still exists but, as far as
  this audit could find by searching every call site, is **not called anywhere in
  `MainActivity.kt`, `BleIqosTransport.kt`, or `UsbIqosTransport.kt`** - the code comment at the
  top of `IqosResponse.kt` confirms it was deliberately superseded ("The old decoder ... silently
  mis-decoded settings replies as battery readings"). It is dead code kept for reference; nothing
  was done to it since removing dead code was outside the scope of this task ("do not remove any
  existing feature").
- **USB path:** `UsbIqosTransport.receive()` calls the exact same `IqosResponse.decode()`. Same
  decoder, different transport.
- **State accumulation:** `DeviceSnapshot.applyResponse()` takes the decoded `IqosResponse` and
  either updates a typed field (battery, firmware, telemetry, settings, ...) or increments
  `framesUnknown`.

## 2. Where unknown frames are classified/logged (before this audit)

Three separate, independent mechanisms existed, none of which kept history:

1. `DeviceSnapshot.framesUnknown` / `lastUnknownHex` - a running count + the single most recent
   unknown hex string. No timestamps, no per-UUID breakdown, no history.
2. `MainActivity`'s `onFrameDecoded` callback - on every `IqosResponse.Unknown`, overwrites
   `DebugActivity.diagnosticMap["Unknown Frame"]` with `"<hex>  (<reason>)"`. A single mutable
   `LinkedHashMap` entry - each new unknown frame erases the previous one.
3. `AppLogger` - a 300-line **in-memory** ring buffer (`CopyOnWriteArrayList<String>`, capped at
   `MAX_LOGS = 300`), never written to disk, with plain `"[TAG] message"` text lines, not
   structured data. Useful for "what just happened" but not for pattern analysis after the fact.

**There was no code anywhere that stored a history of unknown frames, grouped them by UUID or
content, computed occurrence counts, or correlated them with device state/time.** This is exactly
the gap section 6 below fills.

### 3.2 SCP frame layout (documented in `IqosCommands.kt`, verified against `IqosResponse.kt` and the unit tests)

```
byte 0 : 0x00 normal frame, 0x01 continuation frame (multi-frame sequences)
byte 1 : kind    0xC0 = stick/device-wide, 0xC9 = holder, 0xD2 = FlexPuff bus, 0x08/0x90 = replies
byte 2 : header/opcode
byte 3 : register
byte 4+: payload, ending in a per-command checksum byte (not a generic CRC - verified in comments)
```

### 3.3 Message families actually decoded (`IqosResponse.decode`)

| Header/register | Kind | Meaning | Min length |
|---|---|---|---|
| `88 00` | `C0`/`08` | Firmware version (stick / holder) | 10 |
| `88 03` | `C0`/`08` | Product number, ASCII | >4 |
| `90 22` | any | Telemetry (puff count tag `0x8E`, day counter tag `0x17`) | 6 |
| `80 02` | any | Timestamp / days in service | 6 |
| `88 21` | any | Battery voltage, mV, little-endian | 7 |
| `86 23` | `C0` | LED brightness (`0x64`=high, `0x1E`=low) | 9 |
| `84 23` | `08` | Vibration trigger flags | 9 |
| `8B 04` | `08` | Holder charge-start vibration flag | 19 |
| `85 22` | `90` | FlexPuff state | 9 |
| `84 25` | `08` | FlexBattery mode | 9 |
| `87 24` | `08` | Generic on/off setting reply (Auto Start=1, Pause Mode=2, Smart Gesture=4) | 9 |
| anything else | any | `Unknown(hex, "هدر ناشناخته (HH HH)")` | - |

All of the above is exercised by `IqosProtocolUnitTest.kt` with concrete byte-for-byte test
vectors (battery voltage, timestamp, telemetry, firmware, product number, brightness, vibration
flags, charge-start vibration, FlexPuff/FlexBattery, on/off settings, and the two "must reject"
cases for short/garbage frames). Nothing in this audit changed any of the assertions or the
decoder logic they test - see section 12 (Build verification).

### 3.4 Commands (`IqosCommands.kt`)

Fully catalogued reads: stick firmware, holder firmware, stick product number, holder product

## 4. The critical architectural finding: how "unknown" frames are actually produced

This is the most important, fully verified (not inferred) fact in this audit, and it directly
explains both the 196-frame count and the specific frame in this task.

In `processIncomingBytes()`:

```kotlin
val isBatteryChar = characteristic.uuid == IqosProtocol.DEVICE_BATTERY_CHAR_UUID ||
    characteristic.uuid == IqosProtocol.STANDARD_BATTERY_LEVEL_CHAR_UUID

val response = if (isBatteryChar) {
    IqosResponse.decodeBatteryCharacteristic(data)
} else {
    IqosResponse.decode(data)     // <-- runs for EVERY other characteristic, unconditionally
}
```

`IqosResponse.decode()` was designed and documented (its own KDoc says so) for exactly one
source: the SCP control point (`e16c6e20-...`). But the code above calls it for **any**
characteristic that isn't the battery characteristic - including the Device Information ones
(handled separately, before this point, so they're fine) and, critically, **any other
notifiable/readable characteristic the device exposes that the app has never modeled**, such as
`77f38a30-2b2c-489a-be71-29e93a04a90a`.

This happens because of `enableAllNotifications()` (`BleIqosTransport.kt`, ~line 610), which -
intentionally, per its own comment ("harmless, and it surfaces live data the hard-coded list
never asked for") - subscribes to notifications on **every** characteristic on the device that
supports NOTIFY/INDICATE, not only the ones already known. This is a deliberate, reasonable
design choice (surface everything rather than silently drop it), but it has a side effect nobody
had connected before this audit: **every frame from every one of those "extra" characteristics is
then forced through the SCP decoder**, which was never built to understand them, and which will
therefore report them as "Unknown" 100% of the time regardless of what they actually contain.

**Verified fact:** for the specific frame in this task, `77f38a30-2b2c-489a-be71-29e93a04a90a` is
neither the SCP control point, nor the battery characteristic, nor any of the six standard
Device Information characteristics. It falls straight into the `else -> IqosResponse.decode(data)`
branch above. This is not a hypothesis - it is a direct reading of the `if/else` in the file.

**Consequence for the 196-frame population:** it is very likely (STRONG INFERENCE, not proven
without the raw capture) that a meaningful fraction of the 196 unknown frames are not malformed
or unrecognised *SCP* frames at all, but perfectly normal frames from one or more *other*
characteristics/services that the app has simply never had a decoder for. Mixing "SCP frame with
a header we don't recognise" and "frame from a completely different protocol family, misrouted
through the SCP decoder" into one "Unknown" bucket has, until this audit, made it impossible to
tell the two apart. Section 6 fixes exactly this by recording, for every captured frame, which
decode path actually ran (`SCP_DECODER`, `SCP_DECODER_MISROUTED`, `BATTERY_DECODER`, or
`DEVICE_INFO:<label>`), so a future export can separate "genuinely unrecognised SCP frame" from
"frame from an unmodeled characteristic".

## 5. Analysis of `00 20 01 01 00` on `77f38a30-2b2c-489a-be71-29e93a04a90a`

**Bytes:** `00 20 01 01 00` (5 bytes)

### 5.1 What is VERIFIED FACT (directly checkable in the code, no interpretation needed)

- This UUID is not `SCP_CONTROL_POINT_UUID`, not either battery UUID, and not any of the six
  Device Information UUIDs. It is therefore routed into `IqosResponse.decode()` purely by the
  `else` fallback described in section 4, **not** because the app identified it as an SCP frame.
- Under the SCP layout the code assumes, `kind = bytes[1] = 0x20`, `header = bytes[2] = 0x01`,
  `register = bytes[3] = 0x01`. The value `0x20` for `kind` does not match any kind byte used
  anywhere else in this codebase (`0xC0`, `0xC9`, `0xD2`, `0x08`, `0x90`, or the `0x00`/`0x01`
  frame-vs-continuation marker at byte 0). Header `0x01`/register `0x01` likewise matches none of
  the documented header/register pairs in section 3.3.
- At 5 bytes, this frame is **too short to be a Firmware frame** (requires ≥10 bytes) and **too
  short to be a Product Number frame in the documented form** (requires >4 bytes payload after a
  4-byte header, i.e. effectively longer than 5 total). So even if this frame *had* arrived on the
  SCP characteristic, the existing, tested decoder rules would still correctly classify it as
  `Unknown` - the length and header simply do not fit the firmware/version family. This is a
  directly checkable fact from `IqosResponse.decode()`'s own guard conditions
  (`bytes.size >= 10`, `bytes.size > 4`, etc.), not a judgment call.
- The UUID's structure (128-bit, vendor-specific, formatted like the other confirmed PMI/IQOS
  UUIDs already in `IqosProtocol.kt`) is consistent with it being a genuine vendor
  characteristic rather than a coincidental unrelated BLE service.

### 5.2 STRONG INFERENCE (reasonable conclusions, not proof)

- This is very likely a **status/flag-style characteristic**, not a firmware/version
  characteristic, not telemetry, and not a command/response control point. Reasoning: the
  documented telemetry family in this protocol carries 8-byte tagged blocks starting 6 bytes in
  (`90 22` frames are always ≥14 bytes for even one tag); the documented firmware family is fixed
  at 10 bytes with a `major.minor.patch.year` layout at bytes 6-9. A flat, static-looking 5-byte
  payload with a `01 01` pair and a trailing `00` looks structurally like a small
  state/capability/flags register (e.g. "feature X: version 1, sub-state 1, reserved 0") - the
  same *shape* several already-known settings replies in this protocol take (`87 24` frames are
  9 bytes with a setting id and 0/1 value at fixed offsets), just on a completely different,
  unmodeled service.
- Given it was captured only after `enableAllNotifications()` subscribed indiscriminately, and
  given no command in `IqosCommands.kt` ever targets this UUID, this frame was almost certainly
  received as an unsolicited **notification**, not as a response to anything the app asked for.
  That argues against it being a request/response protocol member (nothing requested it) and for
  it being either a periodic status push or a one-time announcement (e.g. on connect).

### 5.3 SPECULATION (explicitly not claimed as fact)

- Whether `01 01` means "version 1.1", "enabled + valid", "type 1 sub-type 1", an index pair, or
  something else entirely - **unknown, and not guessable from one sample**.
- Whether the trailing `00` is a reserved byte, a checksum, a flag, or padding - **unknown**.
- Whether this characteristic relates to the charger/case module specifically (as opposed to the
  holder or stick) - **unknown**; nothing in the one captured value indicates which physical
  sub-system it belongs to.

### 5.4 Direct answer to "does it belong to firmware update / OTA / DFU?"

**No evidence supports that conclusion, and this audit does not make it.** Specifically:

- It does not match the standard BLE DFU service UUID pattern (Nordic DFU and most vendor DFU
  implementations use a small number of well-known 128-bit UUIDs; this one does not match any
  publicly documented DFU/OTA UUID this audit could check against).
- It does not match this codebase's own firmware-version frame format (section 5.1).
- There is no write command anywhere in `IqosCommands.kt`, `IqosProtocol.kt`, or any other file in
  this project that targets this UUID or that resembles a DFU trigger/bootloader-entry command.
  Nothing in the existing, working command set touches this characteristic at all.
- A single static 5-byte value gives no signal one way or the other about update mechanisms -
  DFU/OTA control points are almost always **written to** (to trigger a transfer), not read as a
  passive status value, and no write to this UUID has ever been sent by this app.

**Conclusion for this frame:** classified as **device state/diagnostics family, unconfirmed
sub-type** - not firmware, not telemetry, not command/response, not proven to be update-related.
Confidence: low-to-moderate on "state/flags-shaped", very low on anything more specific.
**What would confirm it:** capturing this same characteristic's value while deliberately changing
device state (charging vs not charging, locked vs unlocked, heating vs idle, right after a
firmware-version read, right after a puff) and checking whether the value changes and in what
byte. That is exactly what the new logging layer in section 6 is built to make possible, using
only observation - no writes to this UUID are performed anywhere in this change.

## 6. Diagnostic logging layer added (new, additive, read-only)

**New file: `app/src/main/java/com/example/iqoscontroller/FrameForensics.kt`**

A passive, thread-safe, in-memory recorder (same pattern as the existing `AppLogger`, capped at
4000 entries so it can't grow unbounded). It does not decode, interpret, or alter anything - it
only observes frames that already flow through the existing transports, exactly like `AppLogger`
already does for its text log. For every frame it records:

- `timestamp` (epoch ms)
- `uuid` (characteristic UUID)
- `direction` (`"RX"` or `"TX"`)
- `hex` (raw bytes)
- `length`
- `appState` (current `DeviceState`, e.g. `READY`, `CONNECTED`, `DISCONNECTED` - see note below)
- `commandContext` (the most recent outgoing command's tag, only if sent within the last 4
  seconds - lets you see "this notification arrived shortly after we sent the FlexBattery
  command")
- `occurrenceForThisUuidHex` (how many times this exact UUID+content pair has been seen)
- `msSincePreviousGlobal` / `msSincePreviousSameUuid` (timing deltas)
- `classification` (which decoder path actually produced this frame - see section 4;
  `"Firmware:SCP_DECODER"`, `"Unknown:SCP_DECODER_MISROUTED"`, `"DEVICE_INFO:Firmware Revision"`,
  etc. This is derived mechanically from which `if` branch ran, never guessed.)

Previous/next frame (as requested in the task) are computed at **export time** by looking at
list adjacency - there's no need to store forward/back pointers on every record for that.

**Honest limitation, stated plainly:** the task asked for context tags like "charging, heating,
puff, button press, pause, lock, settings change". This codebase has **no sensor or decoded
signal for charging/heating/puff/button-press as live events** - `DeviceState` only models the
*BLE connection lifecycle* (`DISCONNECTED, SCANNING, CONNECTING, CONNECTED,
DISCOVERING_SERVICES, READY, BUSY, ERROR`), not device activity. Inventing a
"heating/puff/charging" detector that doesn't exist anywhere in the current protocol
implementation would be exactly the kind of guess the task explicitly forbids. What
`FrameForensics` honestly *can* and does provide as state context is: (a) the real connection
lifecycle state, and (b) which known command (if any) was just sent - e.g. "Lock", "FlexBattery",
"Brightness High" - which does capture "during a settings change" accurately, because that is
something the app actually knows.

**Hook points added (all pure side-effect calls, zero behaviour change to existing logic):**

- `BleIqosTransport.processIncomingBytes()` - one `FrameForensics.record("RX", ...)` call at the
  top (captures literally everything, before any branching), plus `FrameForensics.classify(...)`
  calls in the Device-Info branch and right after the main decode call.
- `BleIqosTransport.writeScp()` - one `FrameForensics.record("TX", ...)` and one
  `FrameForensics.noteCommandSent(tag)` call, alongside the pre-existing `AppLogger`/
  `onRawPacketReceived` calls it already had.
- `UsbIqosTransport.transmit()` / `receive()` - the same two hooks, using the pseudo-UUID
  `"usb:scp"` since USB has no GATT UUID.
- `MainActivity.updateUiState()` - one line, `FrameForensics.currentAppState = state.name`.

None of these change what any function returns, what gets written to the device, or how any
existing UI element behaves. They are exactly as invasive as the existing `AppLogger.i(...)`
calls that were already present next to every one of them.

**Where to see it / export it:** a new "Protocol Forensics (read-only)" card was added to the
**existing, already-isolated `DebugActivity`** (`activity_debug.xml` / `DebugActivity.kt`) - not
to the main app UI, per the task's explicit instruction not to touch the UI. It shows a live
summary (counts, RX/TX split, unknown-frame groups by UUID+content with occurrence counts) and
has three buttons: **Refresh**, **Export JSON** (writes a timestamped file to
`getExternalFilesDir(null)` - no storage permission required, standard app-scoped storage), and
**Clear**. The JSON export includes, for every captured frame, the full field list above plus the
computed previous/next frame hex.

This is intentionally the full extent of the new instrumentation: it observes and reports, it
never writes anything to the device, and it never runs unless the user opens the existing debug
screen.

## 8. Comparison with public information (point 11)

- **VERIFIED FACT:** the codebase's own comments state its command/response frames were sourced
  from a specific public reference (`hauntedfail/iqos` GitHub project / the `iqos` Rust crate on
  docs.rs), and that anything not published there was deliberately left unimplemented rather than
  guessed (see `IqosCommands.kt` header comment). This audit did not have live internet access to
  re-verify that external source's current content, so this is reported as "what the code claims
  and appears internally consistent with" rather than independently re-confirmed against the
  live reference today.
- **VERIFIED FACT:** IQOS ILUMA-family devices (holder + separate pocket charger, no removable
  heat-stick electronics in the classic sense) are a two-piece system, which matches this
  codebase's `kind` split between "stick/device-wide" (`0xC0`) and "holder" (`0xC9`/`0x08`)
  framing.
- **STRONG INFERENCE:** the three separate version numbers the user reported (charger software
  v135.5.0, stick/body firmware v135.5.0.33, holder firmware v124.6.0.114) do not map cleanly
  1:1 onto this codebase's two firmware fields (`stickFirmware` from kind `0xC0`, `holderFirmware`
  from kind `0x08`). It is plausible that "charger software" and "holder firmware" are the same
  physical module reported two different ways by PMI's own app (the charger *is* commonly called
  "the holder" in ILUMA terminology) and that `stickFirmware` corresponds to "stick/body
  firmware" - but this audit found **no verified byte-level evidence** distinguishing a third,
  separate "charger" version stream in the current protocol implementation, and does not claim
  one. Treat this mapping as unconfirmed until checked against a live device.
- **SPECULATION avoided:** no claim is made about PMI's official IQOS Web App or its update
  protocol beyond what's already in this codebase's own comments, since this audit had no way to
  inspect that separately.

## 9. Whether a firmware-update check is safely possible without flashing (point 12)

**What is safely possible and was NOT yet built (see section 10 for why):**
Reading the device's own reported current versions is already fully safe and already implemented
(section 7) - `stickFirmware`, `holderFirmware`, `stickProductNumber`, `holderProductNumber`, plus
the standard GATT `firmwareRevision`/`softwareRevision`/`hardwareRevision`/`modelNumber` strings.
All of this is read-only, uses only already-published, already-tested commands, and requires no
new protocol work.

**What is NOT safely possible without further, real information:**
Determining whether a *newer* firmware exists requires comparing the device's reported version
against PMI's actual current released version for that model - and that comparison data does not
exist anywhere in this codebase, in any public library this project already depends on, or in any
file in this repository. There is no bundled "latest known version" table, no update-server URL,
and no API client for one. Implementing a "checks for update" feature that actually determines
whether an update exists would require **one of**:
1. A confirmed, documented PMI/IQOS backend endpoint that returns current released
   firmware/holder/charger versions for a given model, called strictly read-only (GET) - not
   present in this project and not something this audit fabricates, since inventing a URL or
   response format would violate the "no guessing" and "no undocumented writes" constraints just
   as much as inventing a BLE command would.
2. A user-supplied/maintained reference table of known released versions, kept outside the app
   and simply compared locally against the device's reported version - technically safe (still
   100% read-only towards the device) but requires the user to supply and maintain that data,
   since this project has no legitimate way to know PMI's release schedule.

**What this audit does NOT do:** it does not add a fake "Checking for updates..." feature that
silently always says "up to date" or pings an invented endpoint. That would be worse than not
having the feature. If the user can point to a real, documented, read-only version-check endpoint
PMI's own app calls, that can be added safely in a follow-up - but it must be identified first,
not assumed.
